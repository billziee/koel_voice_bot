# KOEL — Telephony v4 (full parity: barge-in, hold+RAG, escalation, recording, dialer, DTMF)

> Supersedes [TELEPHONY_V3.md](./TELEPHONY_V3.md). v3 built the streaming-session ingest seam and called the PSTN bridge "seam ready — not built," with DTMF and the outbound dialer explicitly left as "remain to build." v4 (PR #65, `telephony/session.py`) builds the bridge into a real, tested, feature-complete transport and closes out DTMF and the dialer, so nothing in that list is still a stub.

## v4 state

**Full parity confirmed.** `TelephonyCallSession` (`telephony/session.py`, ~450 lines) is the phone-transport twin of `ws/handler.CallSession`: constructed with the same session/settings/store/orchestrator/bargein/clients/escalations/monitor collaborators, then `bind()`-ed to a `TwilioMediaBridge` + an ingest instance built from its own callback methods, then `run()`. Every gap the pre-v4 audit found is now closed:

- **Barge-in**: two distinct Gate 1 mechanisms feed the one shared Gate 2 classifier. The buffered ingest (`TelephonyAudioIngest`, RMS-endpointed, no true STT partials) fires `on_voice_activity` the moment energy crosses threshold while the bot is speaking; the session then waits `single_word_interrupt_ms` and, if the caller is *still* talking, calls `_confirm_barge_in` directly — there's no partial text to run the classifier's own backchannel/word-count logic against on this path. The streaming ingest (`StreamingTelephonyIngest`, Deepgram) instead gets true interim partials, so `on_partial` runs the full `TelephonyBargeInGate.evaluate_partial` (same `BargeInClassifier` the browser uses) with a wall-clock-derived `speech_duration_ms` standing in for Deepgram's missing per-partial duration field. Both paths converge on the same `_confirm_barge_in` → `bridge.send_clear()` (a Twilio `clear` frame, immediate playout flush).
- **No-input timeout**: `_no_input_watchdog` polls every 1s against the same reprompt/close windows and `pipeline/silence.on_no_input` policy the browser uses. This is a real mechanical difference from the browser's precise single-shot timer (which blocks on the next socket frame) — telephony has no equivalent single "next event" to wait on, so it's a coarser poll. Functionally equivalent at the 1s-vs-8s window granularity involved; not a gap.
- **Smart-turn hold + speculative RAG**: identical merge-window mechanics to the browser (`SmartTurnAnalyzer.is_complete`, `merge_transcripts` for a follow-up landing inside the hold), riding the newly-extracted `SpeculativeRagCoordinator` (`pipeline/specrag.py`) so both transports share one fire/resolve/cancel implementation instead of the browser keeping a bespoke inline copy.
- **Human escalation — the one genuine, now-fixed gap**: before this PR, nothing called an escalation-registration path for telephony at all, so a PSTN call parked in `waiting_agent` was never actually reachable by an operator, *and* `on_utterance` had no `waiting_agent` guard — the bot kept running full turns and talking straight over the customer during a live handoff. `_sync_escalation` now registers `deliver`/`resolve` callbacks with `EscalationHub` on the first turn that escalates, and `on_utterance` returns early (customer audio still buffered for the recording, but no bot turn runs) while `status in (waiting_agent, ended)`.
- **PSTN warm transfer**: `start_warm_transfer` uses Twilio's Conference API directly (not TaskRouter, which would need a provisioned Workspace/Workflow/TaskQueue this project has no live account to set up or verify) — the live customer call is REST-redirected into `<Dial><Conference>`, and a second outbound call rings the operator with a whisper before joining the same room.
- **REST-driven call termination**: `end_twilio_call` exists because closing the Media Streams WebSocket does not reliably end a PSTN call — that depends on whichever TwiML verb opened the stream. `_end_call_leg` calls it only for a genuinely orchestrator-initiated mid-call end (opt-out, scripted close, no-input close, budget cap); a clean carrier-initiated `stop` frame is already a no-op REST call since Twilio already knows the call ended.
- **Idle-frame watchdog**: `TwilioMediaBridge.run()` wraps each frame read in a 30s timeout (`_DEFAULT_FRAME_IDLE_TIMEOUT_S`) — Media Streams sends a frame roughly every 20ms for the life of a real call (comfort-noise media keeps flowing even during silence on the line), so total silence on the socket this long means a wedged TCP connection (NAT/firewall drop), not a quiet caller. Same failure class the browser's heartbeat timeout catches; Media Streams has no ping/pong of its own, so this read timeout is the analogue.
- **Redis CallSid persistence**: `on_started` (fired from `TwilioMediaBridge._on_start`) saves `state` the instant the `start` frame's `callSid` lands. This exists specifically so the warm-transfer operator endpoint's own `SessionState.load()` sees a real `twilio_call_sid` instead of a stale `None` — without it, a warm transfer had no call to attach to.
- **Bidirectional call recording**: fixed for BOTH transports, not just telephony. Every call recording — browser included — previously buffered only the bot's outbound audio; the customer's voice was never captured. `_buffer_recording_audio` now appends bot WAV chunks (`on_outbound`, already WAV-framed) and customer PCM16 (`on_utterance`, WAV-wrapped via the new public `tts/mixer.pcm16_to_wav` helper), captured regardless of call state — including mid-hold speech during an escalation — so the recording reflects the whole conversation. This matters directly for the roadmap's verbal-consent feature (2.3), which needs to hear the customer's actual affirmative response.
- **Postgres persistence**: `_finalize()` now calls `persist_call(state)` unconditionally at end-of-call (previously telephony calls were invisible to call history, analytics, and QA scoring — the audit found they were never persisted at all). A persistence failure leaves the state in Redis for a later retry rather than silently dropping the call.

**Outbound dialer (1.2), now built end-to-end.** `campaigns.py` claims due `DialAttempt` rows (`FOR UPDATE SKIP LOCKED` on Postgres, plain windowed select+update on SQLite) and `pipeline/dialer_worker.run_dialer_loop` drains them forever from `main.py`'s lifespan (conditional on `dialer_enabled(settings)` — all of account SID/auth token/from-number/public URL must be set, same fail-closed dormancy gate every carrier integration in this codebase uses). Before every origination it checks, in order: RBI calling-hours (`is_within_calling_hours` — outside the window, the whole batch is left untouched and rechecked in 60s rather than a full poll cycle) and a DND scrub (`crm.get_customer(...).dnd`, degrading to "not DND" on a CRM lookup failure so a transient outage doesn't starve the campaign). `pipeline/outbound_dialer.originate_call` then places the call via Twilio's REST Calls API with inline `<Connect><Stream>` TwiML pointed at `/twilio/stream?attempt_id=...&bot_id=...`, plus a `StatusCallback` webhook (`/twilio/call-status`) so a leg that never reaches the Stream at all (no-answer/busy/failed/canceled) still reports back into `record_dial_result` for the retry policy.

**DTMF (1.3), now built.** `telephony/dtmf.py`'s `dtmf_to_turn` maps a pressed digit to a per-bot-configured customer utterance (`BotConfig.config["dtmf_map"]`), which `TwilioMediaBridge._on_dtmf` turns into a synthetic `TranscriptResult` (max confidence, zero duration) run through the exact same `orchestrator.handle_final_transcript` path as spoken input — no separate IVR branch to keep in sync. `DtmfSequence` additionally supports free-form multi-digit entry terminated by `#` (with `*` as cancel), for an account/reference number rather than a single menu choice.

**Still not built — a procurement gap, not an engineering one.** Every piece above is real, live-wired code with passing tests (37 new tests this cycle: the specrag coordinator + the telephony session, on top of the pre-existing bridge/ingest/codec/DTMF/Exotel suites) — but there is still no live Twilio (or Exotel) production account or DID behind any of it. `dialer_enabled()`, `end_twilio_call`, `start_warm_transfer`, and the WS route itself all fail closed with no carrier credentials configured, so the whole stack sits dormant exactly the way it's designed to until an account is provisioned. Exotel (1.4) is comparatively less exercised than Twilio and its webhook signature scheme (`verify_exotel_signature`) is an explicitly-flagged placeholder pending confirmation against live Exotel docs.
